# Manage the files in your home

Keep your dotfiles and your everyday tools the way you declared them, on every machine you use.
You describe them in `~/.config/lodi/home.toml`, read the plan, then apply it:

```sh
lodi home init
lodi home plan
lodi home apply
```

The home scope has five commands: `lodi home init`, `lodi home import`, `lodi home plan`,
`lodi home apply` and `lodi home status`. `lodi home init` writes the starting file, and
`lodi home import` is its 1.0 name.

None of this needs `sudo`. The home scope will not:

- change anything outside your home directory, or act on another user's home,
- edit `~/.profile`, `~/.bashrc` or `~/.zshrc` for you,
- overwrite a file you edited by hand unless you confirm it,
- read the content of your files when it writes a starting `home.toml`,
- undo an apply. The way back is the earlier `home.toml`, applied again.

The full list is in [What this scope will not do](#what-this-scope-will-not-do). A project's
tools are covered in [the project scope](project.md), and the machine's packages in
[the host scope](host.md). [The file formats](../SCHEMAS.md) describe every file named here.

## Write a starting home.toml: `lodi home init` or `lodi home import`

```sh
lodi home init
```

```text
wrote ~/.config/lodi/home.toml; next: uncomment what you want, then lodi home plan
```

The file is written where `lodi home plan` looks for it. It is
`$XDG_CONFIG_HOME/lodi/home.toml` when that variable is set. Everything in it is commented out,
so it changes nothing yet:

```sh
lodi home plan
```

```text
0 files: nothing to do
```

What the file holds:

- a `[programs.<name>]` stub for each program lodi can configure that is on your `PATH`, with
  example values, never values from this machine,
- a `[tools]` block with the catalogue tools that are on your `PATH` now,
- two `[home.file]` examples, one with `text` and one with `source`,
- a note naming the files these programs read that already exist here, with the table to move
  each one into.

It opens none of your files. It only checks whether a path exists, so no secret can end up in
`home.toml`. It needs no network, and two runs on an unchanged machine write the same bytes.

To see the file first, print it and write nothing:

```sh
lodi home init --stdout
```

```text
# Generated by `lodi home import`. It copied nothing and read no file in your home
# directory: every table below is commented out and holds no value from this machine,
# so no setting, secret or address of yours is in it. It names no user, no machine and
# no path outside the home directory, and it carries no date and no lodi version.
```

The options:

| Option | What it does |
|---|---|
| `--stdout` | prints the file and writes nothing. It cannot be combined with the other two. |
| `--out DIR` | writes `DIR/home.toml` and nothing else. `DIR` must be inside your home directory. |
| `--force` | replaces an existing `home.toml`, and nothing else beside it. |

Without `--force`, an existing file stops the command with [`E_EXISTS`](../ERRORS.md):

```text
lodi: error E_EXISTS: ~/.config/lodi/home.toml is already there
   = hint: read it, move it, or run it again with --force, which replaces it
```

`lodi home import` is another name for `lodi home init`. It takes the same options and prints
the same output.

## Declare the files you want

Each entry is one file in your home. This `home.toml` declares three:

```toml
[home]
version = "1"

[home.file.".inputrc"]
text = "set editing-mode vi\n"

[home.xdg_config."git/ignore"]
source = "dotfiles/gitignore"

[home.file.".local/bin/hello"]
text = "#!/bin/sh\necho hello\n"
executable = true
```

A `[home.file."PATH"]` path is relative to your home directory. A `[home.xdg_config."PATH"]`
path is relative to `$XDG_CONFIG_HOME`, or `~/.config` when it is not set. Each entry takes
these keys:

| Key | What it does | Default |
|---|---|---|
| `text` | the file's content, written inline | |
| `source` | a file beside `home.toml` to copy. A folder becomes one entry per file in it. | |
| `mode` | the permissions, as an octal string such as `"0600"` | `"0644"` |
| `executable` | `true` sets the mode to `0755` | `false` |
| `state` | `present`, `absent`, or `seed` to write the file once and leave it to you after that | `present` |
| `backup` | keep one copy of what was at the path before lodi took it over | `true` |
| `on_remove` | what happens when the entry leaves `home.toml`: `restore`, `delete` or `keep` | `restore`, or `keep` for a seed |

Give each entry exactly one of `text` or `source`. `[home] min_lodi_version` sets the oldest
lodi that may read the file. The older `[files]` table still works, as
[Moving from `[files]`](#moving-from-files) explains.

A path must stay inside your home. lodi stops before it writes anything:

```text
lodi: error E_PATH_ESCAPE: `../x` is not a path inside the root: it has a `..` component
  --> ~/esc/home.toml:4:12
   = hint: paths in the home scope are relative to the root and may not leave it
```

It lists every mistake in the file in one run, each with its line and column. The codes:

| Code | What to change |
|---|---|
| [`E_PATH_ESCAPE`](../ERRORS.md) | the path leaves your home, or passes through a symbolic link |
| [`E_ATTR_CONFLICT`](../ERRORS.md) | give `text` or `source`, not both or neither, and `executable` or `mode`, not both |
| [`E_DUP_RESOURCE`](../ERRORS.md) | the same path is declared twice, across all three tables |
| [`E_TYPE`](../ERRORS.md) | an unknown key or a value of the wrong type |
| [`E_UNSUPPORTED`](../ERRORS.md) | `[vars]`, `[inputs]`, `[modules]` and `registries` are not read in `home.toml` |
| [`E_VERSION`](../ERRORS.md) | this lodi is older than `min_lodi_version` asks |
| [`E_CONFIG`](../ERRORS.md) | a `source` is missing or not a regular file, or `XDG_CONFIG_HOME` is outside `HOME` |

## Let lodi write a program's configuration

A `[programs.<name>]` table writes a program's own configuration file from a few keys:

```toml
[programs.git]
user.name = "Example User"
init.defaultBranch = "main"
```

```sh
lodi home plan
```

```text
create    .config/git/config        0644    (programs.git)
```

The file it writes starts with a note that lodi manages it:

```text
# Managed by lodi from home.toml [programs.git]. Edit home.toml, not this file:
# a hand edit here is drift, and `lodi home apply` stops on it.

[user]
	name = "Example User"
```

Every table also takes `enable`, `backup`, `on_remove` and `extra`, which is text copied as it
is. For a program with no table, declare its file with `[home.file]`. Any other name stops with
[`E_UNKNOWN_BLOCK`](../ERRORS.md), which lists the ten names below.

| Table | The file it writes | Keys |
|---|---|---|
| `git` | `~/.config/git/config`, and `~/.config/git/ignore` when `ignores` is set | `user.name`, `user.email`, `init.defaultBranch`, `core.editor`, `core.pager`, `pull.rebase`, `push.autoSetupRemote`, `merge.conflictStyle`, `alias`, `ignores` |
| `bash` | `~/.local/share/lodi/home-scope/shell/init.bash` | `env`, `path`, `aliases`, `snippets`, `histsize`, `histfilesize`, `histcontrol`, `shopt` |
| `zsh` | `~/.local/share/lodi/home-scope/shell/init.zsh` | `env`, `path`, `aliases`, `snippets`, `histsize`, `savehist`, `setopt` |
| `fish` | `~/.config/fish/conf.d/lodi.fish` | `env`, `path`, `aliases`, `snippets`, `abbrs`, `greeting` |
| `nvim` | `~/.config/nvim/init.lua` | `leader`, `opt.number`, `opt.relativenumber`, `opt.expandtab`, `opt.ignorecase`, `opt.smartcase`, `opt.termguicolors`, `opt.shiftwidth`, `opt.tabstop`, `opt.mouse`, `opt.clipboard`, `colorscheme` |
| `helix` | `~/.config/helix/config.toml` | `theme`, `editor.line-number`, `editor.mouse`, `editor.cursorline`, `editor.auto-format`, `editor.true-color`, `editor.rulers`, `editor.cursor-shape.insert`, `.normal`, `.select` |
| `alacritty` | `~/.config/alacritty/alacritty.toml` | `font.size`, `font.normal.family`, `window.opacity`, `window.padding.x`, `window.padding.y`, `window.decorations`, `scrolling.history` |
| `kitty` | `~/.config/kitty/kitty.conf` | `font_family`, `font_size`, `background_opacity`, `scrollback_lines`, `enable_audio_bell`, `confirm_os_window_close`, `map` |
| `tmux` | `~/.config/tmux/tmux.conf` | `prefix`, `mouse`, `status`, `base-index`, `escape-time`, `history-limit`, `default-terminal`, `mode-keys` |
| `starship` | `~/.config/starship.toml` | `format`, `add_newline`, `command_timeout`, `scan_timeout`, `character.success_symbol`, `character.error_symbol`, `shells` |

### Shell tables

```toml
[programs.bash]
env = { EDITOR = "nvim" }
path = ["~/.local/bin"]
aliases = { ll = "ls -l" }
snippets = ["snippets/prompt.sh"]
```

lodi never opens `~/.bashrc` or `~/.zshrc`. The apply prints the line to add there yourself.
Fish reads `conf.d/lodi.fish` on its own.

In the shell files a value is single-quoted, so `$`
stays as it is, and a leading `~/` becomes `"$HOME"/`. A `snippets` file sits beside
`home.toml` and is copied in after the typed lines. A `path` entry is added only when it is not
on `PATH` yet, so sourcing a file twice does no harm.

`[programs.starship]` adds one line to each shell file, which starts starship only when it is on
`PATH`. `shells` picks the shells that get the line. Without it, every shell table you declare
gets it, and `shells = []` adds it to none.

### Values each table takes

A value goes on one line of the file. A newline in a value, or a value outside the ranges below,
stops with [`E_TYPE`](../ERRORS.md), and the hint gives the allowed values.

| Key | Allowed values |
|---|---|
| `editor.line-number` | `absolute` or `relative` |
| `editor.cursor-shape.*` | `block`, `bar`, `underline` or `hidden` |
| `window.decorations` | `Full`, `None`, `Transparent` or `Buttonless` |
| `mode-keys` | `vi` or `emacs` |
| `shells` | `bash`, `zsh` or `fish` |
| `font.size`, `font_size` | a number above 0 |
| `window.opacity`, `background_opacity` | from 0 to 1 |
| `scrolling.history` | from 0 to 100000 |
| `editor.rulers` | columns from 1 to 65535 |
| any other number | 0 or more, and at most 2147483647 for nvim, tmux and alacritty padding |

For helix, alacritty and starship, `extra` is TOML added to the typed keys. A key set in both
places stops with [`E_ATTR_CONFLICT`](../ERRORS.md).

### When the program is missing or reads another file

A table whose program is not on `PATH` prints `W_PROGRAM_NOT_FOUND`. lodi still writes its
files and installs nothing. Helix's program is `hx`. An older file the program reads first
prints [`W_SHADOWED`](../ERRORS.md):

| Table | The older file |
|---|---|
| `git` | `~/.gitconfig` |
| `nvim` | `~/.config/nvim/init.vim` |
| `tmux` | `~/.tmux.conf` |

Move its settings into the table, then delete it.

Some programs read these files only from a given version. From 0.13, alacritty reads
`alacritty.toml`. From 3.1, tmux reads `~/.config/tmux/tmux.conf`. Starship 1.26 reads
`~/.config/starship.toml` even when `XDG_CONFIG_HOME` points elsewhere.

## Put tools on your PATH

```toml
[tools]
ripgrep = "latest"
jq = "latest"
```

`[tools]` means what it means in [the project scope](project.md): a version, a catalogue name,
or a `url` with its `sha256`. An unknown name stops with [`E_NO_RECIPE`](../ERRORS.md), which
suggests the nearest names. The apply downloads the tools into your per-user store and links
them into `~/.local/share/lodi/home-scope/profile/bin`. It then prints the line to add to
`~/.profile`, `~/.bashrc` or `~/.zshrc` yourself:

```sh
. "$HOME/.local/share/lodi/home-scope/profile.sh"
```

lodi never adds that line for you. With fish as your shell and no `[programs.fish]`, it prints
`W_FISH_HOOKS` instead, because fish does not read `profile.sh`. Declare `[programs.fish]` and
`lodi.fish` sets up the tools itself. When two tools ship a program of the same name, the first
by name wins, and the other prints `W_BIN_CONFLICT`.

The apply pins the versions it chose in `~/.config/lodi/home.lock`. The next apply reuses them.
With `--locked`, a missing or outdated `home.lock` stops the apply with
[`E_LOCK_STALE`](../ERRORS.md) before anything is written. `lodi gc` keeps the pinned tools and
removes older ones once a later apply has replaced them.

A home in a repository also finds tools in the `recipes/` folder at the repository's root. Name
`kubectl-convert = "latest"` once `recipes/kubectl-convert.toml` is there. A home with no repository
uses the built-in recipes alone. See [the recipe
guide](../../catalogue/README.md#a-recipe-of-your-own).

## Run your own services

```toml
[services."lodi-hs1.service"]
enable = true
linger = true
unit = """
[Unit]
Description=Sleep until stopped

[Service]
ExecStart=/usr/bin/sleep infinity

[Install]
WantedBy=default.target
"""
```

```sh
lodi home plan
```

```text
create    .config/systemd/user/lodi-hs1.service 0644
1 file: 1 create
+ linger (loginctl enable-linger 1000)
+ service lodi-hs1.service (systemctl --user enable --now -- lodi-hs1.service)
```

Name each unit in full, such as `backup.service` or `backup.timer`. `lodi home apply` then
enables and starts it with `systemctl --user`, as you and never as root. With `enable = false`
it is disabled and stopped. A second apply prints `nothing to do`. `sudo lodi apply` does the
same for every home of the machine, each as its own user.

- **`unit`** writes the unit file into `~/.config/systemd/user`. Leave it out for a unit your
  distribution or a package already installed. lodi writes a unit only when you give one, and
  `lodi home init` never copies one.
- **`linger = true`** keeps your services running while you are logged out. lodi turns it off
  again only if lodi turned it on. Over SSH, use `sudo lodi apply` to change it.
- **Take a service out** of `home.toml`, and the next apply puts it back the way it was before
  lodi managed it. A unit lodi wrote is disabled and stopped, and its file is removed:

```text
removed   .config/systemd/user/lodi-hs1.service 0644    (entry removed: no backup was kept)
1 file: 1 remove
~ service lodi-hs1.service (systemctl --user disable --now -- lodi-hs1.service)
- linger (loginctl disable-linger 1000)
```

lodi never reads or changes a user service you did not declare. `git revert` then
`sudo lodi apply` brings the earlier services back.

## See what an apply would change: `lodi home plan`

```sh
lodi home plan
```

```text
create    .config/git/ignore        0644
create    .inputrc                  0644    (backup: first unmanaged copy kept)
create    .local/bin/hello          0755
3 files: 3 create
```

The plan lists one line per file, sorted by path, then a summary. It writes nothing at all.
Each line starts with what an apply would do:

| Word | What an apply would do |
|---|---|
| `create` | write a new file. A note says when a file already there is backed up first. |
| `replace` | back up a file lodi did not write, and replace it |
| `update` | rewrite a file lodi wrote, with the new content you declared |
| `seed` | write a `state = "seed"` file once |
| `adopt` | take over a file that already has the declared content and mode, writing no byte |
| `restore` | put back the original of an entry you removed |
| `remove` | delete the file of an entry you removed |
| `keep` | leave the file of an entry you removed |
| `drift` | report a file you edited by hand |
| `unchanged` | nothing to do |

A `[files]` entry shows `replace` for a new file and `unchanged` for one already right. With no
`home.toml`, the plan stops with [`E_NO_MANIFEST`](../ERRORS.md):

```text
lodi: error E_NO_MANIFEST: there is no home manifest at ~/.config/lodi/home.toml
   = hint: run lodi home init to write a commented starting ~/.config/lodi/home.toml, or write it by
     hand following docs/GUIDE.md's "The home scope" section
```

## Apply your home: `lodi home apply`

```sh
lodi home apply
```

```text
lodi: warning W_REPLACED_UNMANAGED: .inputrc was not written by lodi; the copy it had is kept as
  94029cdb18d5c02ff6fa90c605076e260835fc9a0be378a38847a3f5817192f5-283382f3da0d1465
created   .config/git/ignore        0644
created   .inputrc                  0644    (backup: first unmanaged copy kept)
created   .local/bin/hello          0755
3 files: 3 create
```

The apply checks everything first and writes nothing if a check fails. Then it writes the files
in the order of the plan. Run it again and nothing changes, not even a file's time stamp:

```text
nothing to do
```

What the apply does with the files already there:

- **A file lodi did not write is copied first.** lodi keeps that one copy in its backup folder
  and never overwrites it. The warning above names it.
- **A file that already has the declared content is adopted.** lodi records it and writes no
  byte.
- **A mode that differs is set back.** That loses nothing, so it does not stop the apply.
- **Folders are created at `0755` and never removed.**

Two applies started at once run one after the other. The second prints one line and waits.

### When you edited a managed file

A file you changed by hand stops the whole apply. Nothing is written, not even the other files:

```text
lodi: warning W_DRIFT: .inputrc has changed since lodi wrote it (recorded 6148f023, now 37aa6d9e)
lodi: error E_DRIFT: 1 managed file has changed since lodi wrote it; nothing was applied
   = .inputrc
   = hint: run lodi home status, then lodi home apply --overwrite-drift to take them back
```

Copy your edit into `home.toml`, or take the file back. `--overwrite-drift` keeps the edited
content in the backup folder before it writes the file:

```sh
lodi home apply --overwrite-drift
```

```text
lodi: warning W_DRIFT: .inputrc has changed since lodi wrote it (recorded 6148f023, now 37aa6d9e)
lodi: warning W_DRIFT: .inputrc was taken back; the edited bytes are kept as
  94029cdb18d5c02ff6fa90c605076e260835fc9a0be378a38847a3f5817192f5.drift-37aa6d9ec039b059
unchanged .config/git/ignore        0644
updated   .inputrc                  0644    (drift: the edited bytes are kept in the backup store)
unchanged .local/bin/hello          0755
3 files: 1 update, 2 unchanged
```

### When you remove an entry

Delete the entry from `home.toml` and apply. Its `on_remove` decides what happens. With the
default, `restore`, the original you had before lodi comes back:

```text
restored  .inputrc                  0644    (entry removed: the original is restored)
```

## Check your files: `lodi home status`

```sh
lodi home status
```

```text
lodi: warning W_DRIFT: .inputrc has changed since lodi wrote it (recorded 6148f023, now 37aa6d9e)
ok           .config/git/ignore        0644
drift        .inputrc                  0644    (edited by hand since lodi wrote it)
ok           .local/bin/hello          0755
3 paths: 2 ok, 1 drift
```

Each file is `ok`, `drift`, `missing`, `unmanaged` or `stale-backup`, with the reason. With
`[tools]`, status also says whether your `PATH` has the tools and prints the line to add.
Status changes nothing and exits 0 whatever it finds.

## A home in the host directory

A host folder can hold your home beside the machine's packages, as
`~/lodi/<hostname>/home/<login>/home.toml`. `<login>` is your user name. Point a home command at
it with the folder and the machine's name:

```sh
lodi home apply ~/lodi --host mybox
```

```text
created   .hushlogin                0644
1 file: 1 create
```

`lodi home plan`, `status` and `init` take the same `SOURCE [--host NAME]`. A folder with a
`home.toml` in it is used as it is. Your `home.lock` is written beside that `home.toml`.
`sudo lodi host apply ~/lodi` applies the machine as root, then this home as you. The
[host scope](host.md) explains that order and `--no-home`.

lodi remembers where the last apply read your home from. A command with no `SOURCE` then stops
with [`E_DECLINED`](../ERRORS.md) and names the folder to use:

```text
lodi: error E_DECLINED: the last home apply read ~/lodi/mybox/home/<login>; a bare home verb reads
  ~/.config/lodi
   = hint: name the source: lodi home apply ~/lodi/mybox/home/<login>
```

In a repository, `sudo lodi apply ~/lodi` applies every `home/<login>/` of the machine, each as
its own user. The tools of that home are then pinned in the repository's `lodi.lock`, not in a
`home.lock`.

### Moving from `[files]`

A `[files]` table keeps working. It is `[home.file]` with `content` in place of `text`:

```toml
[files.".inputrc"]
content = "set editing-mode vi\n"
mode = "0600"
```

Each run of `lodi home plan`, `apply` or `status` with a `[files]` table prints one
`W_DEPRECATED` warning, as [the command reference](../CLI.md) lists. The exit status stays the
same. To move a program's copied file to a `[programs]` table:

1. Run `lodi home init --stdout` to see the stub for each program on your `PATH`.
2. Copy the stub into `home.toml` and move your settings into it.
3. Delete the old `[files]` entry.
4. Run `lodi home plan`. The written file replaces the old one, and your old content is kept in
   the backup folder.

## Files lodi keeps

| Path | What it is |
|---|---|
| `~/.config/lodi/home.toml` | the file you edit |
| `~/.config/lodi/home.lock` | the versions of your `[tools]`, written by an apply |
| `~/.local/share/lodi/home-scope/state.json` | what lodi wrote, to compare against next time |
| `~/.local/share/lodi/home-scope/backups/` | one copy of each file lodi took over |
| `~/.local/share/lodi/home-scope/.lock` | makes two applies wait for each other |
| `~/.local/share/lodi/home-scope/profile/bin` | the one folder your tools reach `PATH` through |
| `~/.local/share/lodi/home-scope/profile.sh` | the script you may source yourself |
| `~/.local/share/lodi/gcroots/home` | keeps your pinned tools when `lodi gc` runs |

`home-scope/` and its backups are readable by you alone, whatever your umask, because they hold
copies of your files. A `state.json` or backup list that lodi did not write stops the command
with [`E_STORE_IO`](../ERRORS.md) before anything is written. A store this lodi does not
know stops with [`E_STORE_VERSION`](../ERRORS.md).

## What this scope will not do

- **It does not need root.** Everything it writes is in your home. Under `sudo`, a home command
  acts on root's home, so it prints `W_HOME_SUDO` first. Run it without `sudo`.
- **It does not edit your shell configuration.** lodi prints the line to add and never opens
  `~/.profile`, `~/.bashrc` or `~/.zshrc` on its own.
- **It does not touch a service you did not declare.** No other unit is written, enabled,
  started or stopped.
- **It does not template.** `home.toml` is plain TOML with `${var}` and no expressions.
- **It does not remove a folder**, and it never changes a file's owner or group.
- **It does not undo.** The way back is the earlier `home.toml`, applied again. The one backup
  of a file lodi took over comes back with `on_remove = "restore"`.
- **It does not overwrite your edits** unless you pass `--overwrite-drift`.
- **It does not touch another user's home**, another machine, or the files of the host scope.
- **It does not copy a secret, and it does not remove one.** `lodi home init` reads no file's
  content and copies nothing.
- **It does not install tools until you ask.** The `[tools]` block `lodi home init` writes is
  commented out.

## Where to look when it fails

`lodi home status` tells you, file by file, whether lodi's record and your file still agree.
`lodi home plan` shows what an apply would do. lodi records what it wrote in
`~/.local/share/lodi/home-scope/state.json`. [The error reference](../ERRORS.md) lists every
code.

| What you see | What to do |
|---|---|
| exit 2, no code | fix the command or remove the extra argument. `lodi home` alone prints the help. |
| [`E_NO_MANIFEST`](../ERRORS.md), exit 3 | run `lodi home init`, or write `~/.config/lodi/home.toml` |
| [`E_TYPE`](../ERRORS.md), exit 3 | fix the key or value at the line and column shown |
| [`E_ATTR_CONFLICT`](../ERRORS.md), exit 3 | keep one of the two keys named |
| [`E_DUP_RESOURCE`](../ERRORS.md), exit 3 | remove one of the two entries named |
| [`E_UNSUPPORTED`](../ERRORS.md), exit 3 | remove the table named |
| [`E_VERSION`](../ERRORS.md), exit 3 | install a newer lodi |
| [`E_PATH_ESCAPE`](../ERRORS.md), exit 3 | use a path inside your home with no symbolic link in it |
| [`E_CONFIG`](../ERRORS.md), exit 3 | fix the `source`, `HOME` or `XDG_CONFIG_HOME` named, or run without `sudo` |
